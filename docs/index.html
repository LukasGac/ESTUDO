Visão Geral

estudo-concurso

SPA de flashcards com Spaced Repetition System (SRS) para preparação de concursos públicos. O usuário estuda baralhos de cards (decks), avalia cada card como Errei / Difícil / Acertei, e o algoritmo calcula automaticamente quando aquele card deve aparecer novamente — priorizando o que está mais fresco na memória de curto prazo.

React 18 TypeScript strict Vite 5 Zustand 4 Supabase Framer Motion Tailwind CSS React Router 6 Vitest

Módulos críticos

Os 5 módulos que você precisa entender para não perder uma tarde depurando comportamentos não óbvios.

1

Algoritmo SRS — SM-2 modificado

src/lib/srs.ts

Implementação do algoritmo SuperMemo 2 com ajustes. A função central é calculateNextReview — ela recebe o estado atual do card e o rating, e retorna o novo estado.

Constantes do algoritmo

INITIAL_EASE_FACTOR
2.0 — fator de facilidade inicial de todo card novo
MIN / MAX ease
1.3 / 2.5 — limites do ease factor para evitar intervalos degenerados
WRONG_EASE_DELTA
-0.2 — errar penaliza o ease factor (card fica mais frequente)
HARD_EASE_DELTA
-0.15 — difícil também penaliza, porém menos
CORRECT_EASE_DELTA
+0.1 — acertar melhora o ease factor levemente
HARD_INTERVAL_MULTIPLIER
0.5 — intervalo é reduzido à metade quando "difícil"
MASTERED_REPETITIONS
5 — mínimo de acertos consecutivos para "dominado"
MASTERED_MIN_INTERVAL
21 dias — intervalo mínimo para "dominado" (ambos obrigatórios)

calculateNextReview — código anotado

export function calculateNextReview(card: Card, rating: Rating): SRSResult {
  let { intervalDays, easeFactor, repetitions } = card

  if (rating === 'wrong') {                        // ①
    easeFactor = clamp(easeFactor + SRS.WRONG_EASE_DELTA,
                        SRS.MIN_EASE_FACTOR, SRS.MAX_EASE_FACTOR)
    repetitions = 0
    intervalDays = 0                              // ②
  } else if (rating === 'hard') {
    easeFactor = clamp(easeFactor + SRS.HARD_EASE_DELTA, ...)
    intervalDays = card.status === 'new'
      ? 1
      : Math.max(1, Math.round(intervalDays * SRS.HARD_INTERVAL_MULTIPLIER))
  } else {                                            // correct
    easeFactor = clamp(easeFactor + SRS.CORRECT_EASE_DELTA, ...)
    repetitions += 1
    if (card.status === 'new' || repetitions === 1) {   // ③
      intervalDays = 1
    } else {
      intervalDays = Math.max(1, Math.round(intervalDays * easeFactor)) // ④
    }
  }

  // Status transition
  let newStatus: CardStatus
  if (rating === 'wrong') {
    newStatus = 'learning'
  } else if (repetitions >= SRS.MASTERED_REPETITIONS
           && intervalDays >= SRS.MASTERED_MIN_INTERVAL) {   // ⑤
    newStatus = 'mastered'
  } else if (repetitions >= 2) {
    newStatus = 'review'
  } else {
    newStatus = 'learning'
  }

  const dueDate = intervalDays === 0 ? now : addDays(now, intervalDays)
  return { newIntervalDays, newEaseFactor, newRepetitions, newStatus, newDueDate }
}
①
Wrong sempre vira learning. Ease factor penalizado em -0.2. Repetições e intervalo resetam para zero.
②
intervalDays = 0 significa "agora". O card entra na fila novamente ainda na mesma sessão (3 posições à frente).
③
Primeiros 1–2 acertos sempre forçam intervalo de 1 dia, independente do ease factor. Evita intervalos gigantes logo no início.
④
Crescimento exponencial via ease factor: interval × easeFactor. Com ease=2.0 e interval=10 dias, próximo é ~20 dias.
⑤
Mastered requer AMBAS as condições: repetições ≥ 5 e intervalo ≥ 21 dias. Só uma delas não é suficiente.
2

Storage Layer — persistência dual

src/lib/storage.ts + src/lib/db.ts

Toda persistência passa por storage.ts. Ele grava no localStorage de forma síncrona e chama o db.ts de forma assíncrona (fire-and-forget) quando há um usuário autenticado.

Namespace por usuário

As chaves no localStorage são prefixadas com o userId para isolar dados entre usuários no mesmo browser:

anki_decks_<userId>
Todos os baralhos do usuário
anki_cards_<userId>
Todos os cards (record plano, indexado por id)
anki_session_<userId>
Sessão de estudo em andamento (ou null)
anki_study_goals_<userId>
Meta diária de cards/minutos + streak
anki_daily_stats_<userId>
Histórico de estatísticas por dia (YYYY-MM-DD → DailyStats)
anki_meta_<userId>
Versão dos dados, flag de inicialização
anki_users
Sem namespace — global no browser. Lista de usuários (admin)
anki_auth_session
Sem namespace — sessão de auth global (legado, Supabase gerencia a sessão atual)

Write-through pattern

export function saveCard(card: Card): void {
  const all = getCards()
  all[card.id] = card
  localStorage.setItem(u('anki_cards'), JSON.stringify(all)) // ①
  if (_userId !== 'default') {               // ②
    db.upsertCard(card, _userId).catch(console.error) // ③
  }
}

// Namespace helper
function u(base: string): string {
  return `${base}_${_userId}`    // ④
}

export function setActiveUser(userId: string): void {
  _userId = userId     // ⑤
}
①
localStorage primeiro, sempre síncrono. A UI nunca espera o Supabase para mostrar o resultado de uma ação.
②
Guard de usuário autenticado. Se _userId === 'default', o app está em modo offline e não tenta sincronizar.
③
Fire-and-forget. Erros de rede são logados mas não propagados. Supabase pode estar desatualizado temporariamente.
④
Namespace dinâmico. O userId é um módulo-level var mutável. Muda quando o usuário faz login/logout via setActiveUser().
⑤
Chamado por authStore no evento SIGNED_IN. O momento em que isso é chamado determina quais chaves serão lidas/gravadas dali em diante.

db.ts — mappers snake_case ↔ camelCase

O Supabase usa snake_case no banco. O TypeScript usa camelCase. O db.ts mantém pares de funções cardFromDb / cardToDb para cada entidade. Lotes de cards são enviados em chunks de 500 para evitar payload excessivo.

deckStore — hydrate + applyRating

src/store/deckStore.ts

Store central para decks e cards. O padrão de hidratação é o coração do sistema de sincronização.

hydrate() {
  // Carrega localStorage imediatamente
  const localDecks = getDecks()
  const localCards = getCards()
  set({ decks: localDecks, cards: localCards })  // ①

  const userId = getActiveUserId()
  if (userId === 'default') return  // ②

  Promise.all([fetchDecks(userId), fetchCards(userId)])
    .then(([remoteDecks, remoteCards]) => {
      if (Object.keys(remoteDecks).length > 0
       || Object.keys(remoteCards).length > 0) {  // ③
        localStorage.setItem(`anki_decks_${userId}`,
                               JSON.stringify(remoteDecks))
        localStorage.setItem(`anki_cards_${userId}`,
                               JSON.stringify(remoteCards))
        set({ decks: remoteDecks, cards: remoteCards })  // ④
      }
    })
},

applyRating(cardId, rating) {
  const result = calculateNextReview(card, rating)
  const updated = { ...card, ...result }
  const updatedCards = { ...cards, [cardId]: updated }
  saveAllCards(updatedCards)  // ⑤
  set({ cards: updatedCards })
},
①
UI responsiva imediata. O usuário vê seus dados no mesmo frame. Sem loading spinner para dados que já existem localmente.
②
Modo offline. Se não há userId real, não tenta acessar Supabase. O app funciona completamente offline com localStorage.
③
Guard contra sobrescrita vazia. Só atualiza se Supabase retornou dados. Usuário novo (sem dados remotos) mantém o localStorage.
④
Supabase é a fonte de verdade. Se há dados remotos, eles substituem o localStorage silenciosamente. Mudanças feitas offline antes do sync são perdidas.
⑤
saveAllCards, não saveCard. A cada rating, todos os cards são re-serializados no localStorage. Correto mas O(n) — ver Gotchas.

authStore — Auth flow com listener global

src/store/authStore.ts

O fluxo de autenticação é orientado a eventos, não a chamadas imperativas. O listener é registrado no momento em que o módulo é importado (antes do React montar).

// Registrado no nível do módulo, não dentro do store
supabase.auth.onAuthStateChange(async (event, sbSession) => {  // ①
  if (event === 'INITIAL_SESSION' || event === 'SIGNED_IN') {
    if (sbSession?.user) {
      const session = await resolveSession(sbSession.user.id)  // ②
      if (session) {
        setActiveUser(session.userId)
        useAuthStore.setState({ session, isLoading: false })
      } else {
        await supabase.auth.signOut()   // ③
        useAuthStore.setState({ session: null, isLoading: false })
      }
    }
  } else if (event === 'SIGNED_OUT') {
    setActiveUser('default')
    useAuthStore.setState({ session: null, isLoading: false })
  }
})

async function resolveSession(userId): Promise<AuthSession | null> {
  const timeout = new Promise(resolve =>
    setTimeout(() => resolve(null), 15000))  // ④
  const query = supabase.rpc('get_my_profile').then(...)
  return Promise.race([query, timeout])
}

// login(): 2 passos
async login(username, password) {
  const { data: email } = await supabase
    .rpc('get_auth_email_by_username', { p_username: username })  // ⑤
  await supabase.auth.signInWithPassword({ email, password })
}
①
Listener no nível de módulo. Registrado quando o arquivo é importado — antes do React renderizar qualquer componente. Garante que o INITIAL_SESSION não seja perdido.
②
resolveSession busca o perfil do usuário via RPC get_my_profile (SECURITY DEFINER no Supabase). Retorna username, role.
③
Perfil não encontrado = force logout. Se o auth token existe mas o perfil não, o usuário é deslogado automaticamente.
④
Timeout de 15 segundos. Se o Supabase não responder, isLoading fica false e o usuário vai para a tela de login. Sem loading infinito.
⑤
Login via username, não email. O Supabase Auth usa email internamente. O RPC traduz username → email antes do signInWithPassword.

Migration — localStorage → Supabase

src/lib/migration.ts

Executado uma única vez por usuário, logo após o primeiro login. Sobe todos os dados locais para o Supabase se o banco ainda estiver vazio para aquele usuário.

src/lib/migration.ts — runMigration(userId) 
const MIGRATION_FLAG = (userId: string) =>
  `anki_migrated_to_supabase_${userId}`

export async function runMigration(userId: string): Promise<void> {
  // 1. Guarda de idempotência — flag no localStorage
  if (localStorage.getItem(MIGRATION_FLAG(userId))) return

  // 2. Supabase já tem dados? Não sobrescreve
  const remoteDecks = await fetchDecks(userId)
  if (Object.keys(remoteDecks).length > 0) {
    localStorage.setItem(MIGRATION_FLAG(userId), 'done')
    return
  }

  // 3. Lê dados do localStorage e sobe tudo em paralelo
  const uploads: Promise<void>[] = [
    upsertAllDecks(decks, userId),
    upsertAllCards(cards, userId),
    upsertStudyGoal(goal, userId),
    upsertDailyStats(stats, userId),
    upsertPomodoroState(pomodoro, userId),
    // ... schedule entries, completions, dinos
  ]
  await Promise.allSettled(uploads)  // falhas parciais não bloqueiam
  localStorage.setItem(MIGRATION_FLAG(userId), 'done')
}

A migração usa Promise.allSettled em vez de Promise.all — falhas parciais (ex: erro numa entrada de schedule) não impedem a migração das demais entidades. A flag é gravada no final, então uma migração parcialmente falha pode ser reexecutada se o localStorage for limpo.

Gotchas

Gotchas

Armadilhas, comportamentos não óbvios e detalhes que a documentação esqueceu — e que vão te fazer perder uma tarde se você ignorar.

1
Card errado é reinserido 3 posições à frente, não no fim da fila
Em studyStore.rateCard, quando o rating é 'wrong', o card é inserido em queue[currentIndex + 3], não no push() do fim. Isso garante que o usuário veja o card errado novamente logo em breve, mas não imediatamente. Se a fila tem 2 cards restantes, o card errado vai para o fim mesmo assim (splice trunca). Se você quiser mudar esse comportamento, cuidado: a lógica de isDone = nextIndex >= newQueue.length usa o tamanho após a reinserção.
2
Supabase sobrescreve localStorage silenciosamente no hydrate
Se o usuário editou cards offline e depois abre o app com conexão, o hydrate chama fetchDecks(userId) e, se Supabase retornar dados, sobrescreve o localStorage e o estado React sem aviso. Não há merge — é uma substituição total. Mudanças offline são perdidas se o Supabase não as recebeu antes.
3
saveAllCards serializa TODOS os cards a cada rating
deckStore.applyRating chama saveAllCards(updatedCards) — não saveCard(card). Isso re-serializa e regrava o objeto inteiro de cards no localStorage toda vez que um card é avaliado. Com dezenas de cards é invisível. Com baralhos grandes (centenas de cards), pode causar jank perceptível, especialmente em dispositivos lentos. O culpado é que saveAllCards também dispara db.upsertAllCards no Supabase (em chunks de 500).
4
isLoading começa true — o App pode ficar preso se o listener não disparar
authStore inicia com isLoading: true. Ele só vira false quando onAuthStateChange dispara (evento INITIAL_SESSION ou SIGNED_OUT). Se o cliente Supabase falhar silenciosamente antes de disparar o evento, o app fica em loading infinito. Há um timeout de 15s em resolveSession, mas o próprio evento INITIAL_SESSION pode não disparar se a inicialização do cliente falhar. O App.tsx tem um safety net de timeout adicional para esse caso.
5
Schedule completions NÃO sincronizam com Supabase
saveScheduleCompletions em storage.ts só grava no localStorage — não chama nenhuma função do db.ts. As marcações de "aula concluída" no cronograma são locais e se perdem se o usuário trocar de device ou limpar o browser. As entradas do cronograma (ScheduleEntry) sincronizam normalmente via upsertScheduleEntry, mas as conclusões (ScheduleCompletion) não, apesar de existirem tabelas para isso no Supabase.
6
MASTERED exige DUAS condições simultâneas
Um card só vai para 'mastered' se repetitions >= 5 E intervalDays >= 21. Só ter muitas repetições mas intervalo pequeno não basta. Isso significa que um card avaliado como "difícil" muitas vezes pode acumular repetições mas jamais atingir o status mastered porque o intervalo fica reduzido. Cards mastered são excluídos da fila de estudo por buildStudyQueue.
7
Auth keys não têm namespace de usuário no localStorage
anki_users e anki_auth_session são globais (sem _userId sufixo). Todas as outras chaves têm o sufixo. Isso significa que, em um browser compartilhado, os dados de autenticação podem vazar entre contextos de usuário — a lista de usuários visível para qualquer um que abrir o browser. A sessão de auth é gerenciada pelo Supabase JS SDK (cookie/localStorage próprio), mas o anki_auth_session é um legado que ainda persiste.
8
sessionMinutes é limitado a 120 minutos
No fim de uma sessão de estudo, o tempo é calculado como Math.min(120, Math.round((Date.now() - startedAt) / 60_000)). Sessões com mais de 2 horas sempre contam como 2 horas nas estatísticas diárias e no cálculo da meta de minutos. Isso previne que uma sessão esquecida aberta durante horas inflacione as stats, mas pode frustrar usuários que realmente estudam mais.
